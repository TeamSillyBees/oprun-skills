# 方案契约

以 `tools/list` 的输入 Schema 为准；样例仅说明公开字段。契约 `oprun.external-plan.v1` 由同一 Schema 生成 Go / Python 校验适配。

1. `open_planning` → 用户确认范围 → `planning_context`。
2. 初稿：`write_draft(workspace_id,revision=0,plan,planning_context?,request_key)` → `validate_plan`。
3. `evaluate_plan(workspace_id,revision,request_key)` → `planning_result(workspace_id,task_id)`。
4. 修改：`prepare_draft_edit(workspace_id,revision,edit_scope,request_key)` → `write_draft` 或 `preview_plan_change(workspace_id,revision,edit_id,patch,planning_context?,request_key)`，返回新草稿版本；核价另调 `evaluate_plan`。
5. `import_plan(workspace_id,task_id,version?,request_key)` → 用户在第一方页面“确认并保存” → `change_status(change_id)`。已有项目传 Core 当前 version，不混用草稿 revision。

### 修改范围与只读核价

`edit_scope.mode` 为 `rename`、`remove`、`patch` 或 `replace`。改名只接受声明 `node_ids` 的 `rename_nodes`；删除只移除指定节点和明确声明的非共享需求，自动清理剩余节点中对应的前置引用，其他条款保留。共用文字需要收窄时，以新的、明确范围的 `patch` 单独调整相关字段。

`patch` 声明 `node_ids`、`node_fields`、`requirement_ids`、`plan_fields` 和 `decision_ids`，只能改这些对象/字段；upsert 仍提交该节点的完整原对象加局部差异，不能省略未授权删除的字段。纯决策变更可传空 `patch`。`replace` 只接受完整 `plan`，不放行局部操作的额外改动。修改凭证绑定工作区、基础版本及范围，重连不重置；首次失败后最多再修补两次，不能自动换键重开。范围是客户端声明，不是用户授权证明。

`evaluate_plan` 无论成功、校验拒绝还是下游失败都不写草稿。旧客户端的内联 `plan` 仅在与已保存快照完全相同时可核价；收到 `draft_required` / `quote_input_mismatch` 后先说明差异，需要保存时单独调用写入。旧的无 revision 预览入口不再隐式改稿核价。

### 待确认选择和输入依据

`planning_context` 与每个草稿版本一起保存，结构为 `schema: oprun.planning-context.v1`、`decisions` 和 `inputs`。

- 决策包含 `id,question,requirement_ids,node_ids,options[{id,label}],status,selection`，可附 `source_ref`。未决为 `unresolved` 且 selection 为 null；建议为 `proposed`，转述用户选择为 `user_reported`，两者必须选择有效 option。Agent 不能写 `confirmed`。不传上下文会继承已存内容，局部修改不能删除仍有引用的已知决策。
- 输入包含 `id,consumer_node_id,kind,purpose`。kind 为 `local`、`existing`（附 source_ref）或 `delivery`（附 producer_node_id、deliverable_id）；purpose 为 `design`、`test_double` 或 `execution`。实际执行需要的交付必须由本节点或其祖先产出。可用 `decision_id,option_id` 指定条件分支。
- 未决事项可保存草稿；与当前工作有关的未决选择、无效引用或不可用的前置输入阻断核价/导入。未涉及当前节点/需求的待定事项不阻断。建议可供评估，但确认页明确展示其建议身份；用户确认前不成为已确认事实。旧草稿没有上下文时返回 `context_status=not_recorded`，不能据此声称需求已审核。
- 第一方确认绑定精确 revision 与 context fingerprint。内容变化后旧确认不能批准新版；已接受操作仍使用原回执恢复。代码校验声明的引用与版本，不能证明文字涵盖了全部用户决定，也不能验证自然语言交付是否真正满足需求。

方案含 `schema,title,requirement,requirements,nodes`；预算未知时省略。需求用 `id,text`；节点用稳定 `client_node_id`，依赖使用这些编号，不用数组位置。所有 ID 及引用符合 `^[A-Za-z0-9][A-Za-z0-9_.:-]{0,79}$`；例如 `scan-1` 是编号，“档案扫描”是名称，不把中文名称拼进编号。每个节点有名称、说明、技能、工时、日历天数、前置、交付物及验收项。交付物引用需求，验收项引用交付物。

接口保存草稿的最低要求是节点编号和名称；这是容错下限，不是给用户的方案质量目标。已知的需求、依赖、交付物和验收项应同时写入；未知工时/工期可为 null，不必因此删除其他已知内容。完整评估必须补齐字段。`estimate_basis` 为 `human_baseline`、`ai_assisted` 或 `unknown`；unknown 不能报价。旧 v1 输入未声明时保留原人类基准语义。`effort_range` 为 min_hours/max_hours；工时应落在范围内。`assumptions` 和 `excluded_scope` 记录假设与排除项。

输出新方案前逐节点核对 `description`、`predecessors`、`deliverables`、`acceptance_criteria`；交付物用 `requirement_ids` 指向实际满足的需求，验收用 `deliverable_ids` 指向被检查的成果。即使 Schema 将它们标为可选，也不能因此丢掉已能说明的内容。没有阈值时写明如何取样、比较和确定阈值，不伪造已通过结论。纯改名或删分支沿用原方案的未改字段，不为凑齐此检查重写旧工序。

描述里出现“交付：…；验收：…”不代表已经填写这些数组。输出时将实际交付物和检查条件分别写入对应字段，不能只拼在 `description` 中。下面只示意一个节点的结构，ID 和内容须按实际方案填写，不能作为所有项目的模板：

```json
{
  "client_node_id": "search",
  "title": "订单查询",
  "description": "按订单号查询当前用户有权查看的订单。",
  "predecessors": [],
  "deliverables": [
    {"id": "d-search", "text": "订单查询入口", "requirement_ids": ["r-search"]},
    {"id": "d-access", "text": "查询权限检查", "requirement_ids": ["r-search"]}
  ],
  "acceptance_criteria": [
    {"id": "a-search", "text": "有权限的订单返回对应信息；无权限的订单不返回业务内容。", "deliverable_ids": ["d-search", "d-access"]}
  ]
}
```

这里一个验收同时检查两个成果，所以显式引用两个 ID。**新方案**中为每条需求先确定实际成果，同时写出该成果的验收与两个引用关系，再合并到节点。负面边界也参与覆盖：例如仅交纸质指引而不建设系统，就让指引成果引用这项限制，并在验收检查交付形态；不能只把限制列在 `excluded_scope`。这不授权给用户原稿补造条款。

逐节点计算“交付物 ID 集合 − 验收引用 ID 集合”，结果必须为空；反向差集也必须为空，不能引用别的节点的交付物。再核对“需求 ID 集合 − 全部交付物引用”，不得因条目较短或是否定句而漏项。引用必须对应实际内容；只填 ID 而没有满足要求的成果与检查仍是缺口。此检查与工时是否已知无关。草图仍有未知事项可以保留，但不得把它称为已完成实施或验收。

未知业务选择用现有字段表达，不新增私有状态字段：前置工序交付“经用户确认的规则与示例”，验收是规则已确定且示例结果一致；依赖它的实施工序引用该前置 ID，按确认后的规则交付。未知事项保留在说明中，不能用“待定也可通过”的验收绕开前置。独立部分无需等待该选择。最终图不按数组位置推断顺序：后续节点的 `predecessors` 必须能回溯到它实际使用的产物，输出顺序不等于依赖关系。

例如用户只确定“支持批量导入”，冲突策略还未知。图中可以先规划下列两道工作，而不是替用户选覆盖或跳过；这些是未来验收条件，不代表用户现在已确认：

```json
[
  {
    "client_node_id": "decide-import",
    "title": "确认导入规则",
    "description": "用现有数据样本核对字段与冲突类型，由用户选择处理规则。",
    "predecessors": [],
    "deliverables": [{"id": "rules", "text": "已确认的字段映射、冲突规则及输入输出样例", "requirement_ids": ["r-import"]}],
    "acceptance_criteria": [{"id": "rules-ready", "text": "字段与冲突处理规则已获确认，每种冲突样例都有确定结果，无影响实施的未决规则。", "deliverable_ids": ["rules"]}]
  },
  {
    "client_node_id": "build-import",
    "title": "实现批量导入",
    "description": "按前置工序确认的规则实现导入，不另设默认冲突规则。",
    "predecessors": ["decide-import"],
    "deliverables": [{"id": "import", "text": "批量导入功能", "requirement_ids": ["r-import"]}, {"id": "report", "text": "导入结果明细", "requirement_ids": ["r-import"]}],
    "acceptance_criteria": [{"id": "import-check", "text": "运行前置确认的全部样例，实际结果与预期一致，每条输入可追溯到导入结果。", "deliverable_ids": ["import", "report"]}]
  }
]
```

不要把所有项目都拆成这两个节点；仅在真实未决条件影响后续工作时使用这种依赖。未知估算仍可留空，不能编造一个工时来取得评估通过。

最终序列化先判断任务来源。**由用户需求生成方案**：以全部用户消息为事实基线，`requirements.text` 摘录实际要求，保留否定、量词、时间和条件的原有作用范围。工程工作写在节点，不伪装成用户需求；助手先前的草图、问题选项及未获答复的建议都不是已确认原稿，可以重拆、补齐和纠错。未知分支放入 `unknowns` 和前置确认工作，不能在需求或排除项中先选定；已明确的成果不能重新降为待选。

先完成内容核对，再序列化，不从上一条助手表格直接转写。对新方案做一次双向检查：

- 从用户原句到需求：目标、否定限制和既有条件都没有漏掉或扩大；现状条件没有被转换成新的业务目标。
- 从每个必做动作回到依据：由用户明确要求、已选分支或完成该目标所必需；否则改为待确认分支。`unknowns` 中仍未选择的事项，不能在任一节点、交付或验收中已有唯一答案。“按确认规则”不是前面擅定动作的免责短语。
- 从验收到输入：实际使用的接口、环境、规则及其他节点成果，在本节点或祖先中有实际交付，不能仅有设计或申请说明。未决分支如果选另一路，整条下游仍能成立；否则调整下游，不是删除未知项来制造确认。
- 从目标到检查：引用 ID 和实际内容同时覆盖每条目标及限制；不能只引用“加快/改善”却仅验收“功能存在”，也不能漏列否定需求来让差集为空。

**局部修改用户提供或明确确认的原稿**才从原对象应用最小差异：`remove_nodes` 不表示删除依赖它的工序，共用回归只移除相关前置、专属对象；重复的删除请求若已满足则不再改稿。**仅核价或恢复时 `plan` 与原对象及已授权改动保持相等**，包括不存在的字段继续不存在；最终输出整稿不等于授权补全。缺少的说明、交付、验收或引用在方案之外报告。不要同时执行上面的新方案补齐步骤。

已有 `budget` 是用户上限，不是平台报价；报价待核不能使预算丢失。新方案已知预算用数值型 `budget`，未知预算省略，不能填 null。不同交付可以由同一验收检查，但要列出实际覆盖的全部 ID，不靠相近名称推定引用存在。按公开 Schema 检查字段类型和枚举；格式问题与业务内容缺口分别报告，不通过改写只读原稿来消除检查结果。

未知可选文本直接省略，不能填空字符串；例如未取得公开来源地址时省略 `source_ref`，也不能编造链接。空数组仅表达确实没有条目，如首道工序的 `predecessors: []`。`oprun_validate_plan` 会分别指出交付约定与估算缺口；先保留已知交付约定，再补有依据的估算，不为消除错误捏造事实。

Patch 仅支持命名字段：`title,requirement,budget,clear_budget,rename_nodes,upsert_requirements,remove_requirements,upsert_nodes,remove_nodes,assumptions,excluded_scope`。省略表示保留；upsert 替换完整对象；空数组清空假设，clear_budget 明确清空预算。改名条目为 `{client_node_id,title}`，不重新分配编号。删掉的节点编号不能给另一个工作复用。整体图未完整时可保存，评估前必须消除悬空依赖、环和未覆盖需求。

删除节点并不等于删除全部下游：共用下游仍有保留需求时，用 `upsert_nodes` 保留其编号与既有职责，仅移除被删分支的前置、交付和验收内容。不能用级联删除来消除悬空依赖。版本只取工具回执；未调用工具的建议稿沿用来源版本作为对照，不宣称系统产生了新版本。

请求体 128 KiB，单 patch 96 KiB，草稿总量 256 KiB，单工序交付约定 14,000 字节。大图分次写入草稿后按版本评估；分片不会放宽总量限制。金额最多两位小数，后台使用一致的规范化序列化，不接受自定义价格、费率、执行人或签署字段。

连接范围与持久草稿分开。重新授权后携带 workspace_id 并重新确认当前范围。报价从完成时起 30 分钟可用，确认页面 5 分钟；已接受命令恢复时沿用原决策和幂等键，仍由 Core 核验当前权限和项目版本。并发修改、权限移除、报价过期都不能静默跳过。

已有项目保留执行人、资金和运行能力配置。草稿金额采用平台工序报价合计，可能不同于用户预算上限；确认页必须展示差异。新方案只准备未签署快照。工具不提供签署、派单或支付能力。

交稿前按来源执行其中一项最终核对：

- **从需求新建或继续拆解**：输出当前完整工作安排，而非标题提纲。`requirements` 非空；每个节点都有说明、前置、非空交付物和非空验收数组，两个引用关系完整。业务选择仍未知时，先规划取得该选择的工作，再按选择实施并验收；未来验收条件并不冒充现在已确认。不能以“下一步再补交付物和验收”为当前整稿的替代。Schema 中兼容旧草稿的可选字段不降低这一交稿要求。
- **局部修改、仅核价或恢复用户原对象**：先复制原对象全部字段，再应用截至本轮明确授权的差异；最后比较每个字段的有无与内容。删除一个功能只收窄相关节点、需求正文、需求条目和引用，仍有效的需求及字段不能一起丢掉。原本没有的字段也不能擅自补造。说明、未知事项和下一步写在方案之外，不能拿它们替代应保留的原字段。

新建方案在输出 JSON 前再逐条对照用户原句，而不是上一轮助手摘要，检查需求、排除项、每个节点和验收是否引入了下面的语义变化。有则先修正再交稿：

| 用户表达 | 图中应保留的意思 | 不成立的推断 |
| --- | --- | --- |
| 某类业务仍按原规则处理 | 所有入口都遵守原规则；入口适用范围未指定时待确认 | 自动禁止这类业务使用新入口，或其他业务免于原规则 |
| 某项业务逻辑别改 | 相同业务输入仍按原有逻辑产生相同结果 | 禁止原有模块被调用、禁止数据产生正常变化 |
| 暂不要求某种能力 | 本次不用专门建设或以它作为交付目标；已有工具自带不妨碍使用 | 验收要求这种能力不存在、不可用或必须移除 |
| 现有系统只能以某方式接入 | 先确认是否接入；若接入，按已知限制实施 | 默认必须向该系统写入或导出，未选择的分支成为必做 |

未知分支采用条件成果与对应验收，例如“若选用外部归档，完成归档接入；否则交付已确认的本地保存路径；验收按所选路径核对记录可取回”。不能写一个固定动作再加“按确认规则”掩盖分支尚未选择。交付有条件时，后续工作也使用该条件，不能让未选分支阻塞全部工作。

验收同时检查引用与真实因果：跨模块的用户操作只能在相关功能和可用环境汇合后检查；前置中只有设计文档不等于功能已完成。异步结果查证、迁移增量导入与实际恢复等必要工作应有可执行动作和结果，不能只在风险提示或回退计划中提及。
